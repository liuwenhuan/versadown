# 网盘下载并发能力设计

## 背景

迅雷分享下载在应用和系统代理配置保持不变时，8 路 Range 连接会在下载数 MB 后收到空响应；同一短效下载地址、请求头和代理改为 1 路后可持续下载。现有实现仅把应用级 `maxConnectionsPerServer` 作为 aria2 全局值，无法表达不同网盘的安全上限，也无法限制同一网盘同时进入下载引擎的任务数。

## 目标

- 每个网盘声明统一的下载并发安全上限：单文件连接数和同时提交到下载引擎的任务数。
- 个人网盘文件与分享文件走同一套能力解析、槽位调度和 aria2 参数生成逻辑。
- 用户设置继续表达期望值；实际值始终为用户设置与网盘安全上限的较小值。
- 等待网盘任务槽位时不解析短效 URL，避免排队期间地址过期。
- 保留代理下载，不引入代理绕过或直连降级。
- 应用单任务连接数默认值从 8 改为 4，但不迁移已有设置。

## 非目标

- 不把安全上限描述为网盘厂商公开承诺的最大值。
- 不改变普通 HTTP、FTP、BT 或磁力任务的并发模型。
- 不自动覆盖用户已经保存的 `maxConnectionsPerServer`。
- 不在本次改动中启用天翼云盘。

## 能力模型

在网盘注册表增加：

```rust
pub struct DownloadConcurrencyPolicy {
    pub max_connections_per_file: u8,
    pub max_concurrent_tasks: u16,
}
```

`ProviderDescriptor` 通过 `download_concurrency` 暴露该策略，前端 DTO 使用 camelCase。两个值均为不可由用户突破的安全上限，并在注册表构造时保证大于零。

初始策略：

| 网盘 | 单文件连接数上限 | 同时任务上限 | 依据 |
| --- | ---: | ---: | --- |
| 夸克 | 1 | 4 | 经配置代理的只读四段 Range 现场验证返回 HTTP 412，按失败降为 1 |
| PikPak | 4 | 4 | 当前连接器生成可分段直链；以应用新默认值作为保守产品上限 |
| 百度 | 4 | 4 | 当前连接器已有 Range 探测；以应用新默认值作为保守产品上限 |
| 阿里 | 4 | 4 | 对象存储协议支持并发分段；以应用新默认值作为保守产品上限 |
| UC | 4 | 4 | 当前连接器生成直链；以应用新默认值作为保守产品上限 |
| 迅雷 | 1 | 4 | 给定分享链接经同一代理的对照测试证明 1 路稳定、8 路失败 |
| 天翼 | 1 | 1 | 连接器当前采用串行保守策略，且产品未启用 |

后续只读四段 Range 现场验证若失败，应把对应单文件上限降为 1；验证成功仅证明当前连接器、账号、代理和服务端路径可承受 4 路，不代表厂商永久保证。

## 有效并发计算

共享函数计算：

```text
effectiveConnections = min(settings.maxConnectionsPerServer,
                           provider.downloadConcurrency.maxConnectionsPerFile)

effectiveProviderTasks = min(settings.maxConcurrentDownloads,
                             provider.downloadConcurrency.maxConcurrentTasks)
```

aria2 单任务提交必须同时设置 `split` 与 `max-connection-per-server`，避免只覆盖其中一个值造成参数不一致。普通非网盘下载继续使用 aria2 进程的全局设置。

## 共享任务调度

新增 `CloudDownloadScheduler`，按 `CloudProvider` 维护 FIFO 槽位。个人文件和分享文件提交前先创建只含稳定来源的本地任务，然后进入调度：

1. 持久化安全的待提交信息：任务 ID、网盘、目标目录、输出名、覆盖/续传标志；不保存签名 URL、Cookie、Authorization 请求头或代理密码。
2. 调度器按注册表安全上限批准任务。槽位满时任务保持 `queued` 且没有 aria2 GID。
3. 获得槽位后重新读取当前代理设置，验证任务仍可运行，再解析稳定 `cloud://` 或 `cloud-share://` 来源。
4. 将新解析的 URL、请求头和有效单文件连接数一次性提交给 aria2。
5. 任务完成、失败、取消或回收后释放网盘槽位并唤醒同网盘下一个任务。

调度槽位表示“已获准进入下载引擎且尚未终止”的网盘任务。它可能因为 aria2 的全局任务上限短暂处于 waiting 状态；这种保守计数不会突破网盘安全上限。

应用重启时，调度器先从数据库恢复仍带 GID 的活动网盘任务占用，再恢复没有 GID 的持久化待提交请求。若旧版本遗留的活动任务已超过新上限，只允许它们自然结束，不再批准新任务。

## 任务控制与恢复

- 等待槽位且无 GID 的任务可以暂停：状态变为 `paused`，调度器不会解析 URL。
- 恢复等待任务：状态回到 `queued` 并重新进入同网盘 FIFO。
- 取消等待任务：状态变为 `cancelled`，删除待提交请求并唤醒等待器。
- 调度或解析失败：任务变为 `failed`，释放槽位；重试重新创建待提交请求。
- 已有部分数据、payload 文件和有效 `.aria2` 控制文件时，重试使用续传；仅有预分配 payload 时要求覆盖并从零开始。这一规则沿用现有修复。
- 重试同样受网盘任务槽位和单文件连接数上限约束，并重新解析短效 URL。

## 数据与安全边界

- 新的持久化请求表只保存稳定来源可推导之外的本地提交参数。
- URL、请求头和认证信息只存在于获得槽位后的短生命周期内。
- 调度时使用用户当前配置的代理；不尝试绕过代理，也不在失败后自动改为直连。
- 注册表是唯一的网盘并发能力来源，连接器和命令层不得按网盘名称重复分支。

## 前端契约

- `ProviderDescriptor` 增加 `downloadConcurrency`，便于设置页、诊断与后续队列说明使用。
- 设置默认值 `maxConnectionsPerServer` 从 8 改为 4；已有后端设置文件保持原值。
- 本次不新增可编辑的“网盘上限”控件，避免把安全上限误解为用户偏好。

## 验证

- 注册表契约测试覆盖全部网盘的两个非零上限和明确矩阵。
- aria2 选项测试覆盖用户值高于、等于和低于网盘上限，以及 `split`/`max-connection-per-server` 同步。
- 调度器测试覆盖同网盘 FIFO、不同网盘独立、终态释放、暂停/取消等待任务、重启恢复和旧活动数超过上限。
- 个人与分享提交测试证明 URL 只在获得槽位后解析，并证明两类任务共享额度。
- 默认设置的 Rust 与前端定向测试覆盖新值 4，且保存值 8 不被迁移。
- 现场测试使用当前代理，对每个有可用会话和足够大文件的网盘发起四个互不重叠的小 Range 请求；不输出签名 URL、Cookie 或 Authorization。
