# 下载输入验证设计

## 目标

所有进入本地下载、网盘分享或 aria2 的来源都必须先通过格式验证。格式不正确的输入不创建任务、不调用下载引擎，并向用户显示安全且具体的本地错误。已有任务的确认和重试同样复核来源，避免旧数据库记录或 IPC 调用绕过前置检查。

## 架构

后端提供单一的 `validate_download_input` 管线。它先从原始文本按出现顺序提取候选（包括已知协议的残缺写法与已登记网盘域名），再对每一项返回 `Validated` 或带稳定中文错误文案的 `Invalid`。`Validated` 包含已确定安全的规范化来源与任务类型；未知文本不降级为直链。`prepare_download`、`parse_download`、确认和重试路径只接收这个已验证的投影，下载服务仍在提交边界按照任务来源复核。

前端在提交粘贴内容时先调用新的预扫描 IPC。单条有效直链维持立即开始的现有体验；多候选文本进入串行确认器。每个候选都显示 `N/M`，有效项复用已有确认窗口，错误项显示原因且仅提供“跳过并继续”与取消。已确认的项继续保留，取消不会创建尚未处理的项。

## 验证规则

- 磁链必须有 `magnet:?`、至少一个 `xt=urn:btih:`，BTIH 值只能是 40 位十六进制或 32 位 Base32；查询参数可保留原样，不重写哈希。
- ED2K 只接受 `ed2k://|file|name|size|32-hex-md4|/` 的文件形式，文件名非空且尺寸为无符号整数。
- HTTP(S) 和 FTP 必须能由 URL 解析器解析，scheme、主机、端口和认证部分符合可提交 URI 的约束；HTTP(S) 的无查询 Unicode 路径可百分号编码，含查询的 URL、签名和片段绝不被解码或重写。`.m3u8`、`.mpd` 与 `.torrent` 仅在有效 HTTP(S) URL 上分类。
- 迅雷链接的 Base64 包装及其解码目标均须有效；目标只可为已经支持的 HTTP(S)、FTP、ED2K 或磁链，不能将任意文本交给 aria2。
- 网盘分享只接受注册表声明的精确 host、`http/https`、默认端口、匹配的路径前缀及非空分享 ID。看似网盘地址但未通过这个规则的项是网盘格式错误，不得降级为直链。
- 本地种子路径仍通过现有文件读取/大小限制流程，在提交前校验扩展名和非空绝对路径。

IPC/RPC 使用 Rust `String`/JSON 的 UTF-8，不引入字符集转换。错误消息不得包含完整签名 URL、FTP 密码、访问码或 RPC token。

## 数据流与状态

`预扫描 -> 已验证候选/错误候选 -> 单项确认 -> create/prepare -> 提交复核 -> aria2`。预扫描不写数据库。创建任务后如果本地复核或 aria2 拒绝失败，任务调用现有 `fail` 转为失败态；引擎错误的用户文案仅在确认 URI/magnet 参数语义无效时归类为“下载引擎拒绝该链接：链接格式无效”，普通 HTTP 400 保留为“下载引擎拒绝请求（HTTP 400）”。

已签名的网盘下载 URL 是受控连接器生成的瞬态内部 URI，不能按用户直链规则重写；其来源仍由稳定的 `cloud-share://` 标识和网盘解析流程保障。

## 前端交互

`NewDownloadDialog` 和顶栏入口共用批处理会话状态。它存储预扫描结果、当前索引、已完成项与取消状态。单一有效直链沿用自动开始。混合文本或多项输入会显示“正在处理 N/M”；合法项在确认后继续，合法但无需元数据的直链也被确认。无效项不可提交，只可跳过。访问码提示停留在当前分享项。

## 测试与验证

Rust 测试覆盖每类有效/无效来源、Unicode URL 的安全规范化、伪造网盘地址、迅雷解码目标、创建前零副作用及确认/重试防线。前端 Vitest 覆盖串行进度、无效项跳过、取消保留已创建项和单直链自动开始。按项目规则运行相关 Rust 测试、相关前端测试（排除 `.worktrees/**`）和 `npm run build`；发布构建另行运行 `scripts/build-windows.ps1`。
