# 迅雷原生续传与假速度排查（2026-09-20）

## 证据与根因

使用本机安装目录中的官方 `DownloadSDKProxy.dll` / `DownloadSDK.dll`，未启动 Thunder.exe、未改系统代理、未修改用户现有任务。

1. `XL_QueryTaskInfo` 的 924 字节结构中，偏移 44 是连接计数，不是下载速度。可控 HTTP Range 下载停止后，该字段仍为 1，实际接收字节完全不变。原实现 `max(该字段, 进度增量)` 因此永远可以显示 1 B/s。偏移 48 为当前连接计数，52/60/68 为源站/其他资源累计接收字节；新实现用本次任务接收字节增量和实际采样时长计速，不把恢复出的历史完成字节当作新流量。
2. `XL_StopTask` 成功不等于释放任务。仅 stop 后 create，同一输出仍受旧 SDK 任务占用；本地对照中完成计数回到零，并重新请求文件头。对照采用 stop、等待停止状态、`XL_DeleteTask` 释放句柄（保留磁盘断点）、再 create/start 后，Range 从未完成位置继续，完整文件内容校验一致。直接 start 旧句柄的对照也停在状态 5，没有新数据，不能替代释放重建。
3. SDK 状态映射错误。该版本接口返回：1 初始、3 下载、5 停止、7 完成、8 失败。原实现按 4 完成、1 失败处理。完成状态 7 已通过最终文件重命名和逐字节校验验证，也对照了 DLL 内部的状态转换函数。
4. 原生后台仅凭令牌注入和历史进度设置 SVIP；前端又强行保留这个标记。现在令牌接受不直接显示 SVIP：需要当前任务在有效令牌下有新增非源站资源字节，且最近 5 秒内有相应流量证据。超时清除，不以预分配大小、历史进度或连接计数代替加速流量。
5. 旧监控协程会追踪数据库里的“最新 GID”，暂停恢复后可能同时监控新任务。现在监控固定绑定启动时的 SDK ID。SDK ID 仅属于当前进程，恢复时按本进程实际持有的输出路径释放旧任务，不再拿数据库遗留数字 ID 操作新进程里的任务。
6. SDK 把创建 URL 作为断点资源身份。云盘每次解析得到的临时签名 URL 不同，直接用新 URL 重建同一个 `.xltd` 会报 201。本地源只改签名参数也稳定复现，证明不是登录或限速。现在以文件 GCID 建立稳定的 SDK 资源标识，创建后、启动前调用 `XL_RedirectOriginalResource` 更新为真实直链；该标识不是云盘 API 请求地址，不向它发起下载。缺少 GCID 的契约仍使用原 URL，不能声称该情况已经覆盖了变更 URL 的跨进程恢复。

## 为什么旧验证漏掉了

- ABI 单测先按猜测偏移写入数值，再从同一偏移读回，不能验证官方结构。
- 旧实测只要求重新建任务后累计完成量超过暂停前的数值；重新下载也能满足。
- 检查目录内任意文件的非零前缀可能读到 `.cfg`，不能证明数据文件完整。

- `vitest run --dir src src/lib/downloadEvents.test.ts src/components/DownloadQueue.test.tsx --exclude '.worktrees/**'`：86 通过。先观察到清除过期 SVIP 的回归失败，再修复通过。
- 加强后的同一官方 DLL 集成测试：旧签名失效返回 403，新签名下载相同内容。修复前跨进程立即错误 201；修复后保留 1,835,008 字节，跨进程完成 16,777,216 字节并逐字节校验，25.03 秒通过。SDK 更新源时会请求 Range 0–20479 做内容探测；断言允许这 20 KiB 探测，但禁止大的有效下载范围从零重下。

## 真实账号验收与追加根因

磁盘保存的 API 会话请求返回 HTTP 401；独立测试的密码恢复返回 `WebAuthorizationRequired`。这**不能证明应用内网页登录状态无效，也不能据此要求用户重新授权**。

用户随后反馈应用内仍可访问网盘。对照确认运行中应用与测试的数据目录、代理配置一致；但独立测试直接创建 `XunleiClient` 并尝试密码恢复，遗漏了实际应用 `recover_authorization → recover_in_order → capture_persistent_authorization` 的持久化网页会话静默恢复步骤。迅雷密码插件本身通过网页流程登录，独立密码恢复返回 `WebAuthorizationRequired` 并不是网页恢复失败的证据。

后续在隔离目录复用用户的持久化网页资料，运行现有应用隐藏测试实例，通过实际 `cloud_list_directory` 命令完成恢复：成功读取 7 个根目录条目，保存新会话。没有退出用户登录、清除凭据或操作现有任务。测试实例的 `WEBVIEW2_USER_DATA_FOLDER` 必须指向复制的迅雷资料；指向空目录会覆盖恢复 WebView 的目录配置，导致错误地测试空登录态。

真实 `midysj.zip`（128,543,808 字节）已验证：同进程暂停、释放旧句柄、重建后保留断点，并出现新加速资源数据。但跨进程重新解析 URL 时发现此前本地固定 URL 验证没有覆盖的问题：

- 新签名 URL 与原 URL 不同；使用新 URL 创建同输出路径任务，两次立即返回状态 8、错误码 201、完成量 0。
- 同一断点改用原 URL 创建任务，可以继续传输。对照在 162.93 秒完成全部 128,543,808 字节，新累计接收 87,501,485 字节，其中非源站资源 81,408,676 字节；ZIP 内 1 个条目 CRC 校验通过。
- 该对照只证明 DLL 与会员通道可用，以及 URL 身份变化影响断点恢复；**原 URL 可能过期，不能把复用旧 URL 当作生产修复**。

接入正确的源地址更新流程后，再做真实云盘完整验证：

- 新任务先下载 898,153 字节，暂停继续后增长到 1,983,517 字节，并出现新非源站流量。
- 退出该测试进程，新进程重新解析文件，确认新旧 URL 不同，恢复已有断点并再次注入当前任务的会员规则。
- 最终完成 128,543,808 字节；恢复阶段新增接收 107,712,771 字节，其中非源站资源 100,502,681 字节；189.36 秒，SDK 完成状态 7，最终文件已重命名。
- ZIP 的 1 个条目 CRC 校验通过。验证目录为 `.tools/xunlei-native-cloud-63W6Qm`，与用户任务目录隔离。

Proxy 的更新源 ABI 经本机二进制核对为 `int(task_id, wchar_t* url, uint32_t utf16_length)`，长度不含 NUL。Proxy RVA `0xE683` 写长度、`0xE6B4` 乘 2 序列化；Server RVA `0x8CCB` 自补 NUL，`0x8D23` 调用直接 DLL。直接 DLL 的同名函数仅两参，不能混用。未用 `XL_ContinueTask`：该函数用于 HTML 检查后的继续，不是普通暂停续传。

云盘测试允许通过 `ALLDOWNLOADER_XUNLEI_FILE_ID` 指定用户报告文件（仍校验名称为 `midysj.zip`），避免错误假设文件位于根目录。必须显式提供隔离的 `ALLDOWNLOADER_XUNLEI_SESSION_ROOT`；相同 `ALLDOWNLOADER_XUNLEI_DOWNLOAD_ROOT` 第一次运行验证暂停继续，第二次设置 `ALLDOWNLOADER_XUNLEI_RESTORE=1` 验证新进程完整恢复。最终测试只保存 URL 摘要用于确认地址变化，不保留原 URL 或“强制旧直链”分支。

按开发期规则没有为旧版“临时 URL 身份”断点增加迁移或兼容分支，也没有删除用户旧下载。已验证的是修复后的新建任务及其暂停、跨进程恢复；不能据此保证旧版生成的断点能直接接续。未编译新版应用进行 UI 端到端验证。

本次验证未编译或替换应用发布二进制。
